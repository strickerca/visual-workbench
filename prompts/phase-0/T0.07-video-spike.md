## Goal

Measure what getting PC pixels to the phone costs on this hardware: hardware HEVC encode on the Iris Xe, decode on the phone, JPEG dirty tiles, and lossless frames.

## Steps

1. Test source: a window that changes every frame and shows a frame counter, plus a static "UI-like" window with text.
2. `tools/bench/video-pc` (Rust, windows crate; add to the workspace):
   - Capture the chosen window with Windows.Graphics.Capture at native resolution, with MinUpdateInterval set explicitly.
   - Record frame arrival times and DirtyRegions (Windows 11 24H2 API).
3. Encode with the Media Foundation hardware HEVC encoder (MFTEnumEx, hardware flag), with low-latency mode on, no B-frames and a capped bitrate.
   - Feed D3D11 textures without CPU copies (DXGI device manager). Use oneVPL only if Media Foundation misbehaves; check its license first.
   - Measure per-frame encode latency (submit → output) at a 1440×3088 portrait crop and at full 3840×2160, with the bitrate.
4. Save the Annex-B streams and push them to the phone.
5. `tools/bench/video-android`:
   - Decode with MediaCodec using KEY_LOW_LATENCY=1, the Qualcomm vendor low-latency keys and a maximum operating rate.
   - Measure queue → output latency per frame, render to a SurfaceView, and record which decoder was used.
6. JPEG dirty tiles: for typical UI changes (typing, scrolling, cursor blink), encode only the dirty regions as JPEG q85 with a permissively licensed encoder. Measure per-frame encode time and bytes, and the frame rate reachable over USB when 10–25% of a 1440p window changes per frame (STREAM-001's test condition).
7. Lossless frames: encode a 4K frame as PNG (fast compression) and as QOI; measure time and size.
8. Write p50/p95 for each measurement in docs/evidence/T0.07.md. Append a dated D9 entry to docs/DECISIONS.md confirming or revising the approach.
